# ADR-0119: Hand-owned migrations may diverge from the Better Auth schema mirror on column *type*

- **Status:** Accepted
- **Date:** 2026-07-15
- **Relates to:** ADR-0010 (auth runtime), ADR-0118 (account identity uniqueness); migrations 0001 (BA identity), 0073 (onboarding columns), 0077 (user.email → citext)

## Context

The Better Auth identity tables (`user`, `session`, `account`, `verification`) are generated by the Better
Auth CLI. We keep a checked-in mirror of that output at
`packages/db/db/migrations/.better-auth.schema.sql`, and a CI "schema drift guard" regenerates from
`apps/auth/src/auth.ts` and `diff`s it against the mirror. The invariant, stated in 0001's header, was that
the migrations reproduce the generator output verbatim so a regenerate "diffs cleanly."

Two forces break that invariant cleanly:

- **Added columns** (0073: `firstName`, `lastName`, `onboardedAt`) — resolved by declaring them as Better Auth
  `additionalFields` in the generator config, so the mirror *also* gains them and stays in sync.
- **Changed column *types*** (0077: `user.email` `text` → `citext`) — Better Auth has **no** way to express
  `citext`; the generator will only ever emit `text`. There is no config edit that makes the mirror match.

So `user.email` is the first case where the live schema must intentionally differ from the mirror.

## Decision

**A hand-owned dbmate migration may ALTER a Better-Auth-generated column to a type the generator cannot
express, provided the mirror is left as the generator emits it and the divergence is documented.** This is
safe because of *what the drift guard actually compares*:

> The guard diffs the **mirror file** against **fresh generator output**. It never inspects the live migrated
> database. As long as we do not edit `.better-auth.schema.sql`, the two agree (both `text`) and the guard
> stays green. The live column (`citext`) diverges by design.

Requirements for such a migration:

1. **Do not touch `.better-auth.schema.sql`** — it stays as the generator emits it.
2. **Document the divergence in the migration header** — name the column, the live type, the mirror type, and
   why the generator can't express it, so a future reader doesn't "fix" the mirror to match.
3. **Preserve Better Auth's runtime assumptions** — the type must accept everything BA reads/writes. `citext`
   is a drop-in supertype of `text` for BA's lowercased email values; BA keeps lowercasing on write, and
   citext makes the uniqueness case-insensitive at the DB regardless.
4. **Keep the migration reversible** — text↔citext is not binary-coercible, so drop the dependent constraint,
   ALTER with an explicit `USING` cast, and recreate; the `down` restores `text` + the original constraint.

## Consequences

- Email identity is now case-insensitive-unique at the database, matching `org_invites.invited_email` and
  `orgs.slug`, and independent of Better Auth's app-layer lowercasing — the guarantee an email-change flow
  needs.
- The drift guard remains meaningful for *structure* (columns present, added fields) but no longer certifies
  *type parity* for a column it can't express. That is an accepted, documented gap for `user.email`, not a
  hole to close.
- Future BA-column type changes follow this same recipe; if the divergence set ever grows large, revisit
  whether the mirror should carry annotated overrides instead.
